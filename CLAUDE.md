# silverware-libraries: context for working on this repo

**Silverware**: a collection of plugins (SilverBullet libraries) for [SilverBullet](https://silverbullet.md), installed straight from this repository (`REPO.md` lists them). Each plugin is a folder `silverware-<name>/` (its library page `silverware-<name>.md`, the documentation only (it is the plugin's README too), its `files:` installing beside it the bundle and the pages of its code: `silverware-<name>-init.md` (settings, the JS loaded and its bridge, commands, events), `silverware-<name>-api.md` (the `-- priority: 50` Space Lua API) and `silverware-<name>-style.md` (the CSS), split so on 2026-11-03; the built `silverware-<name>.js`, `src/`, `silverware-table/ui-tests/`), shown as **Silverware <Name>** (its commands `Silverware <Name>: …`), its settings and Space Lua API under `silverware.<name>` (one global `silverware` the plugins share: `silverware = silverware or {}`, then their field; what a plugin's Lua blocks share between them and keep across loads of Space Lua, not API, under `silverware_internal.<name>`, so `silverware.<name>.` completes to the API alone; `config.define("silverware.<name>", …)`: SilverBullet's config splits a dotted key into nested objects, verified in its `client/config.ts`), its CSS classes, data attributes and CSS variables under a prefix of its own. The scripts (build, deploy) list the plugins; vitest, tsc and Playwright find every plugin folder's tests. Renamed from Table Plus (`tablePlus.*`, `tp-`, the repository `silverbullet-libraries`) on 2026-10-22, without keeping the old names: a space using it changes its CONFIG, its scripts (`tablePlus.define…`) and its themes (`data-tp-theme`, `--tp-*`).

The plugins: **Silverware Icons** (`silverware-icons/`, prefix `swi-`, on the branch `feat/icons`, in development: sets of icons (Lucide, emoji) the other plugins draw (`silverware.icons.api`: `markup`, `text`) and pick from (`pick`: a tab per set, a set's groups a row of icons up to ROW_GROUPS else a dropdown; playground/icons.html); [docs/silverware-icons.md](docs/silverware-icons.md), its steps there), **Silverware Toolbar** (`silverware-toolbar/`, prefix `swb-`, on `main` since its branch `silverware-toolbar` was merged: see *Silverware Toolbar* below and [docs/silverware-toolbar.md](docs/silverware-toolbar.md)), **Silverware Tags** (`silverware-tags/`, prefix `swg-`, on `main` since its branch `silverware-tags` was merged: see *Silverware Tags* below and [docs/silverware-tags.md](docs/silverware-tags.md)), **Silverware Chart** (`silverware-chart/`, prefix `swc-`, on `main` since its branch `silverware-chart` was merged: see *Silverware Chart* below and [docs/silverware-chart.md](docs/silverware-chart.md)), **Silverware Database** (in development, `silverware-database/`, prefix `swd-`, on the branch `feat/database`: see *Silverware Database* below and [docs/silverware-database.md](docs/silverware-database.md)), and **Silverware Table** (`silverware-table/`, prefix `swt-`): interactive markdown tables (in-place editing, sorting, filtering, rows and columns, pinning, formulas, column types, copy and paste with spreadsheets). The user-facing documentation is the library page [silverware-table/silverware-table.md](silverware-table/silverware-table.md); this file is the context behind it: how the code is built, what was verified about SilverBullet, and why things are the way they are.

## Commands

```
npm install
npm run build        # bundle silverware-table/src/index.ts into silverware-table/silverware-table.js
npm run verify       # before a commit: tsc (with unused locals), vitest, and the bundle matches src/ (check-build)
npm test             # vitest (unit tests and jsdom UI tests)
npm run test:ui:install  # once: Playwright's Chromium (the version it pins), which the UI tests run in
npm run test:ui      # Playwright: interactions in its Chromium against the playground, which it starts on port 8010
npm run test:ui:open # the same in Playwright's window: tests picked and run one by one, each step's page to look at
npm run test:ui:sb   # the same tests against a real SilverBullet (Docker, the version scripts/silverbullet/Dockerfile names; SB_IMAGE another; on Windows that version's own release, downloaded once into .cache/silverbullet/, nothing installed; SB_BIN a binary of your own), the committed .js deployed; options after -- (--ui, -g)
npm run check        # tsc
npm run playground   # http://localhost:8000/: Silverware Table without SilverBullet, on mock data; /toolbar.html: Silverware Toolbar on a CodeMirror editor; /database.html: Silverware Database's core over the memory store, with debug views (playground/database-views.ts, written against the view API as a user's view is)
npm run deploy -- <space folder>   # copy the library into a local space
```

## Working rules

- **Rebuild before every commit**: `silverware-table/silverware-table.js` is committed, because SilverBullet installs it from the repo and runs no build. A commit with `src/` changes and a stale `.js` ships the old code. `npm run check-build` (part of `npm run verify`) fails on a stale bundle.
- **Commit messages**: [Conventional Commits](https://www.conventionalcommits.org), one line `<type>(<scope>): <description>`, no body, **no AI co-author trailer**. One feature or fix per commit.
  - Types: `feat` (something new for the user), `fix` (a bug), `refactor` (no change in behaviour), `perf`, `test`, `docs` (the library page, README, this file), `build` (bundling, scripts, dependencies), `chore`, `style` (formatting only).
  - Scope: the plugin (`table` for Silverware Table; a new plugin by its name), `playground`, or none for the repository as a whole (`build: …`).
  - A change that breaks what a space has (settings, the Space Lua API, a theme's selectors or variables, stored markdown) is marked `!`: `feat(table)!: …`.
  - The description in the imperative, lowercase, no period: `fix(table): keep the toolbar over a table rendered anew`.
  - History before 2026-10-22 uses `Table Plus: …` / `Silverware: …` subjects.
- **Commit only when the user says so** ("commit"); until then changes stay in the working copy. Never push without being asked; never push to `main` directly unless asked. A change spanning several fixes is split into commits, each with `silverware-table.js` built from its own changes.
- The conversation with the user is in Czech; everything in the repository (code, comments, docs, commit messages) is English.
- **A fix goes where it belongs**: the core gets generic mechanisms only (it knows no module by name, nor a module's classes or settings), a module's fix stays in the module. Features read rows through the host (`bodyRows`, `shownRows`, `cellAt`), never by querying the table's DOM.
- **What SilverBullet runs is not touched for the playground**: the benchmark measures from outside (playground/profile.ts wraps methods); no measuring, flags or checks for it in `src/`.
- Do not write files of a SilverBullet space on disk while SilverBullet has it open: it keeps its copy and writes a sync conflict into the page (it did, in CONFIG.md). Change pages through SilverBullet (its UI, a Silverware Table command).
- Every commit: `npm run build`, then `npm run verify` passes (tsc with `--noUnusedLocals`, which tsconfig does not enforce; vitest; the bundle checked against `src/`).
- A change to how tables are used (pointer, touch, menus, what survives a write) gets a scenario in `silverware-table/ui-tests/`, and `npm run test:ui` passes before its commit (not part of `verify`: it needs a browser and takes longer).
- **Interaction tests go in their plugin's `ui-tests/`** (a new plugin: its own folder and `helpers.ts`, no other plugin's used), which CI runs as a job of its own. **Splitting a plugin's tests into areas** (a folder under `ui-tests/`, a CI job each: `silverware-table/ui-tests/sheet/`) **is the user's decision**: where a plugin's job grows long, propose a split (which areas, how many tests each, the time it would save) and wait; never move tests into such a folder unasked.
- Code style: match the surrounding code. Comments explain why, in full sentences or fragments; user-facing strings and docs are English. The library page is written for users: plain, specific, no internals.
- **No mentions in the pages a space installs** (a plugin's library page and the pages of its `files:`): SilverBullet reads `@name` as a mention wherever `@` follows no word character, `.`, `@`, `+` or `-` (`[@due]`, `(=@projects`, `@tasks` too) and lists the page in its Mention Inbox. Outside code it is written `\@` (`[\@due]`); in a code span or a fenced block it stays as it is. A test whose text is a page's (the Functions, Column types and Conditions tables) compares through `asInLibraryPage` (silverware-table/src/testing/librarypage.ts), and `shared/librarypages.test.ts` fails on any page with one (the user's report, 2026-11-09).
- A check of a value is `validate<What>` (`validateTableName`, `validatePlace`; a member of an offer or helpers `validate`), giving why it does not hold as text, `undefined` where it does (renamed from `<what>Problem` on 2026-11-07; Silverware Tags' helper `nameProblem` kept as an alias for scripts). A result's `{ problem }` is data, not a check, and keeps its name.
- Line endings are LF (`.gitattributes`); editors on Windows may write CRLF into the working copy, git normalizes on commit.
- When editing files from a shell on this machine, heredocs mangle backslashes: write scripts to a file (or use an editor tool) when the text has `\`.

## What was verified in SilverBullet (by probe pages)

Probes were pages with a test table and a one-line Lua expression listing the index, e.g.
`${(function() local p = editor.getCurrentPage() local out = {} for _, row in ipairs(query[[from index.tag "table" where page == p order by pos]]) do … end … end)()}`.
A new `space-lua` block on a page is not active until Space Lua is reloaded; an inline `${(function() … end)()}` needs no reload.

- **Space Lua blocks are in the index** (`plugs/index/space_lua.ts`; queried live on 2026-10-22): `index.tag "space-lua"` gives each `space-lua` block with `ref` `Page@position` and `script` (its text), no `page` field; queried from the API page's Lua while Space Lua loads (as a definition is refused), it has every block. So a refused definition names the pages whose blocks call that API (`callers` in the library page's Lua); the definitions themselves do not say where they come from. The notification stays until closed and has a button per page (at most three) going to the block: `editor.flashNotification(message, type, { timeout = 0, actions = { { name, run } } })`, the options in `client/plugos/syscalls/editor.ts` of SilverBullet's main (verified in the local build; a release before them would ignore the options and close it as any other).
- **`_CTX` is a `${…}`'s own** (2026-11-05, probed in 2.12.1): `_CTX.currentPage` is there in the expression itself, `nil` in a function it calls that was defined on another page (the API page's `silverware.table.evaluate`). And as a page is opened from another, the editor's page is the new one while its text is still the page left: so `evaluate` takes the editor's page where `_CTX` has none, and reads the page as saved where the text does not hold the formula (else `#REF!`: `formulas.spec.ts`, SilverBullet only).

## Maintainability: to revisit

Noted on 2026-10-22: small UI changes had started to take long. A first pass (the same day) took what features repeated into shared helpers of the core (`core/geometry.ts`, `press.ts`, `outline.ts`, `frame.ts`; `core/menu.ts` `floatingMenu`, `menu.ts` `namingThatCloses`; `TableHost.cellUnder` / `rowOf` / `heldBounds`), split the controller (2770 lines to about 1900: `modules.ts`, `core/rows.ts`, `anchor.ts`, `insert.ts`, `toolbar.ts`, `tablemenu.ts`) and added `npm run verify`. What is left:

**Shared helpers come first.** Before writing a feature's own version of something another feature does (geometry, taps, outlines, frames, menus, elements: `el` in shared/elements.ts), look in `core/`, `menu.ts` and `shared/`; when two features need the same thing, it moves there, generic (the core knows no module).
