## Silverware Chart

Charts written in a format other tools draw (Mermaid's `xychart-beta` and `pie` now; Obsidian Charts' planned), drawn in SilverBullet by Chart.js; a chart's data from its block or from a markdown table, followed live. On `main` since its branch `silverware-chart` was merged. The plan, the decisions and what the proof of concept showed: [docs/silverware-chart.md](docs/silverware-chart.md) (*Status and next* first). Built as the others: a core that knows no module, format, type of chart or source; modules turned off (`silverware.chart.modules.<name>.enabled`) not loaded; formats added without changing the plugin (`silverware.chart.defineFormats`). **Charts do not need Silverware Table**: a markdown table is read by the chart itself (the `tables` module: `above`, `below`, `#Heading`, `[[Page#Heading]]` as SilverBullet links to a heading); Silverware Table, where installed, is used only through its public API by a module of its own (`silverwareTable`: tables it named, through `silverware.table.tables`; the charts' data written with its writes, through `silverware.table.onWrite`), and it knows nothing of charts.

Verified in the local SilverBullet (2.12.1 of main, 2026-11-01): a code widget is not rendered anew when what it read changes (unlike `${…}`), so charts follow their tables through `editor:pageModified`; SilverBullet renders each code widget twice, one element never attached; a click on a chart does not open its markdown, SilverBullet's own widget menu shows at its top right; a page's cursor starts at its first line, so a block there shows its markdown; a JS function handed to Lua and given back to JS (`silverware.table.onWrite` through the chart's bridge) is called as it was, and a table's edit with the charts' blocks written in it is one Ctrl+Z.
