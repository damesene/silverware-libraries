# Silverware Icons

Sets of icons (Lucide, emoji) that the other plugins draw and offer to pick from, in the page's colors. **A library for the other plugins, nothing on its own**: no init page, no commands, no settings. Its API page (`-- priority: 50`) imports the bundle and sets `silverware.icons.api` and `silverware.icons.defineSets`. Prefix `swi-`. Uses: Silverware Toolbar (own icons, the Emoji action), Silverware Database (items' and properties' icons).

Plan, decisions (2026-11-10), sizes and steps: [docs/silverware-icons.md](../docs/silverware-icons.md).

## How a value is written

- **`<set>:<name>`** (`lucide:house`) for an icon of a set, in CONFIG and frontmatter alike: plain text that Lua and queries read. **Anything else is text shown as itself**: an emoji is its character (`🏠`), so values written before Silverware Icons existed stay valid.
- Told apart by form alone (`shared/iconref.ts`, pure: `^[a-z][a-z0-9-]*:[a-z0-9][a-z0-9-]*$`), so a plugin reads, checks and keeps a value without Silverware Icons installed or a set loaded. A domain may import iconref.ts.
- The plugins' own rules stay theirs and take a reference whole (the toolbar's `iconOf`, the database's `validateIcon`). No value is dropped because a set is missing; a set gone shows its references as missing, never rewritten.
- Accepted: a text with a reference's form (`a:1`) is read as a reference.

## How a plugin gets it

- A plugin's init page hands `silverware.icons and silverware.icons.api` over in its bridge (the API page, priority 50, runs before the init pages). JS objects through Lua come back the same object, their methods called synchronously (verified in the local SilverBullet, 2026-11-10).
- The plugin calls `iconsOf(bridge.icons)` (`shared/icons.ts`) once and uses what it gets: the API where its `version` is `ICONS_VERSION`, else the **stand-in** (text as itself, a reference a dotted box titled *Needs Silverware Icons*, the picker's place a note linking the library page). Plugins and Silverware Icons are updated apart; a plugin never asks whether it is installed.
- **No plugin imports `silverware-icons/src`**: each plugin's isolation test refuses other plugins' code. Only the playground imports it directly.
- `shared/icons.css` (the `<base>-icon` box and `<base>-icon-missing`) is a template that scripts/sharedstyles.mjs writes into each consumer's style page (`shared-icons` marks). The stand-in's note is styled inline: without Silverware Icons none of its CSS is installed.

## Markup and placeholders

- `markup(value, base)` gives markup in `<base>-icon swi-icon`: text escaped; an icon of a loaded set its SVG; a set still loading a placeholder (`data-swi-icon`, `data-swi-state="pending"`); no such set or icon a stand-in (`swi-missing`, its title why).
- **Markup is meant to be put into the page at once, not kept.** Silverware Icons fills placeholders itself: one pass over `[data-swi-icon]` as a set loads (or a user's set is defined), and while any set loads a MutationObserver of the body fills those added meanwhile, ended `LINGER_MS` (1 s) after the last load. Markup kept out of the document past that stays blank. Plugins know nothing of loading.
- SVG is written by the plugin from nodes (24×24, stroke `currentColor`, width 2, round), only the elements and attributes in `ALLOWED_ELEMENTS` / `ALLOWED_ATTRIBUTES` (set.ts), values escaped; never `style`, `href`, `on*`. Not a protection against a user's set (`defineSets` runs their JS anyway) but so a set of any source cannot break the page.
- `text(value)`: text itself, an icon its label (its set's search data where loaded, else made from its name; a tooltip never loads a file).

## Sets as data

- The code knows no set by name. `src/manifest.ts` is generated by the build (`scripts/icons/index.mjs`): each built-in set's name, label (its tab), kind (`svg` / `text`), license and files. Do not edit it.
- Each set's data is split by who needs it, files beside the bundle loaded through `import.meta.url` (the bundle's URL is the space's: `js.importFromSpace` imports `/.fs/<path>`; verified in the local build and 2.12.1 with its service worker): `silverware-icons-<set>.js` for drawing (nodes, aliases; svg sets only), loaded as an icon is first drawn; `silverware-icons-<set>-search.js` for picking (labels, keywords, groups), loaded as its tab opens. So a favourite's icon at start loads no search data. A file that fails to load is said once and not retried until reload.
- **Adding a built-in set**: a script in `scripts/icons/` returning `{ name, label, kind, license, draw?, search }`, a line in `SETS` (order = tab order), the files in the library page's `files:`. Nothing in `src/`. `npm run build` writes the files and the manifest; `check-build` compares them.
- **Updating Lucide** (`lucide-static`, devDependency): its categories and aliases are in no npm package (checked 2026-11-10), only in Lucide's repository. After updating lucide-static run `node scripts/icons/lucide-meta.mjs` by hand (fetches the tag of the installed version, writes `scripts/icons/lucide-meta.json`, committed), then build. The build fails where the meta's version differs, an icon lacks an entry, or a category or its icon is unknown, so building needs no network.
- **Emoji** come from emojibase-data (`scripts/icons/emoji.mjs`): one search file only (a character needs no drawing data); each group's icon must be one of its emoji or the build fails.
- **The user's sets** (`defineSets`, one file with drawing and picking data): checked by `setOf` (set.ts); a set that is wrong refused whole, a wrong icon left out, said in a notification. A built-in name replaces that set in place. Replaced as Space Lua loads again (`resetDefinitions`): those of before stay until the first new definition.
- Lucide's renames are followed through its aliases (`lucide:home` draws `house`). A set taking another's names (`replaces`) is left for when needed.

## The picker

- One picker (`src/picker.ts`), its markup and CSS Silverware Icons' own, scoped under `.swi-picker` (the toolbar's dialog sets `button { font: inherit }`, which shrank the emoji). The caller gives the element it fills and sets colors and size by CSS variables on it.
- A tab per set in the sets' order, the last used open (localStorage `silverware.icons.lastSet`); `sets` narrows them (one: no tabs). `picked(value)` gets the value as written.
- **Groups as a filter, its look by count, a rule for every set**: up to `ROW_GROUPS` (10) a row of icons over the search (emoji: 9), more a dropdown (Lucide: 43). *All* first; no set is an exception.
- Search with shared/search.ts `findByWords` (labels, keywords, groups' labels); arrows and Enter.
- The last used of every set first (`silverware.icons.recent`, 24). The old lists `silverware.toolbar.recentEmoji` and `silverware.database.recentEmoji` are read in once and removed.
- No windowing: Lucide's 2046 icons in *All* draw in about 106 ms (playground, 2026-11-10).

## Tests and playground

- `/icons.html` in the playground: the picker in a panel, the icon picked drawn as the plugins draw it.
- `ui-tests/`: the picker on the playground (`@playground`), the API from Space Lua against SilverBullet. The picker inside a plugin is tested by that plugin's tests (those picking emoji need Silverware Icons deployed).
- Not measured: the observer's cost while a set loads.
