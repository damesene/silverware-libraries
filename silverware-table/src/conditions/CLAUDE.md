# Conditional formatting (Silverware Table)

## Layout

```
    conditions/        the conditional formatting domain, pure; index.ts its API: api.ts (the public API every definition is written against: Cell, Context, Scope, Style, ParamSpec, FormatDefinition (`style` or `look(cell, context)`), ConditionDefinition (`test(cell, context)`), Helpers), helpers.ts (HELPERS: palette names, `mix`/`gradient` as color-mix text, `levels(styles, split)` a look by levels, `matches` the filter's syntax, `normalize`, `today`, `icons`), scope.ts (`cellOf`, `scopeOf`: statistics computed as asked), style.ts (checked, combined (an earlier rule's property kept), `styleLook`: marks and vars, a palette name by its use: fill, text, solid), params.ts (specs checked, stored params read leniently, `storedParams` only what differs from the default), rule.ts (stored JSON read and written; a rule that does not read kept as written; `at` the order across where rules are stored), custom.ts (definitions checked: a list or a function of HELPERS, each item a definition or a function of HELPERS), registry.ts (built-in ones made through the same checks; custom replacing a built-in of its name in place; `definitionsVersion`), evaluate.ts, builtin/conditions/ and builtin/formats/ (one per file, each a function of HELPERS importing only types from api.ts: a test checks it, and loads each, its types stripped, as a user's file; each listed in the library page's tables)
```

### Conditional formatting (`conditions/`, `features/conditions.ts`; decided with the user 2026-11-03, docs/silverware-table-conditional-formatting.md)
- **Formats are JS, not CSS**: a definition says how a cell looks as data (`Style`), any number of levels and colors, and the core's `CellLook.vars` carries it (custom properties `--swt-*` only, checked by `mergeLooks`); one CSS rule reads them, under `:is(#sb-main, html)`, never `!important` (a theme that uses it wins, accepted).
- **One API for built-in and custom definitions**: a built-in one is a function of HELPERS importing only types, made through the same checks as the user's; its Excel form is its own (`excel`), so nothing outside the definitions knows one by name (reviewed 2026-11-03: Excel's forms had been a table by built-in name, which left custom definitions out of the file); formats set up in the dialog (keywords, number ranges, levels, own style) are built-in formats with richer params (`list`, `style`, `color`, `pattern`, `boolean`), stored in the rule, nothing saved apart.
- The header and pinned rows and columns are never formatted; hidden rows count in a scope (filtering does not reshuffle colors). A whole table's rule is one range as in a spreadsheet (decided with the user 2026-11-03, after it had been each column on its own: "over the whole table" read as the whole table), `perColumn` each column on its own. Rules of a column are stored on it (they follow it); the order across columns and the table is each rule's `at`.
