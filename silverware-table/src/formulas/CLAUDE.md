# Formulas (Silverware Table)

## Layout

```
    formulas/          the formulas domain, one file per part; index.ts is its API for the rest of Silverware Table (re-exports)
      cell.ts          what the formulas read of a table besides values, through `FormulaCells` the formulas module gives (`formulaOf`/`formulaCell`/`withoutFormula`, `rowNames`/`cellNames`): the domain reads no metadata; `calculated` (a view's, a pivot's) and `held` (`HeldFormulas`: formulas a module keeps in a table's metadata row that calculate none of its cells, a choice list's, the column types module's offer: what the table reads, `forFormulas` going through them, their references following edits as a cell's do: `followOwnFormula` in the formulas' write step, `followFormula` in `otherTablesWritten`; every module of the formulas module's `HOLDING` asked, their formulas together); StoredFormula; rowsByName, cellsByName, hasFormulas, formulaCount, forFormulas
      tokens.ts parser.ts   reading a formula: tokens, syntax tree (parsed once per text)
      references.ts    how references are written (A1, ranges, [col], names, tables, pages) and what a table's formulas refer to
      evaluate.ts      calculation: Sheet (a table), Book (the tables referred to), recalculate, the reasons of errors
      edits.ts         formulas through edits: references following rows/columns/renames, calculated columns, formulas removed
      frame.ts         a formula's cell and range references written anew whole, with their table's name (`withAreasWritten`): how the formulas module shows a formula in a frame's addresses (the sheet) and reads it back
      autofix.ts help.ts    a slip fixed (a missing ")"); help and completion while typing
      places.ts        formulas written in a page's text outside its tables: where the host's finder says (`defineFormulaPlaces`, `formulaPlacesIn`: its places checked, within the text, in order, apart); the formulas module's `otherTextWritten` writes them with `followFormula` (edits.ts) in the same edit as the table, the first table of its name only
      page.ts          the page's tables by name (`NamedPageTable`: the names given by the module), other pages read; which tables a write recalculates
      values.ts dates.ts arguments.ts   values and conversions; dates and times; argument handling the built-in functions share
      criteria.ts      conditions of the -IFS functions as spreadsheets write them (">10", "<>done", "app*", "", "<>"), wildcards (SEARCH, XLOOKUP's match_mode 2)
      function.ts      the shape of a function (FormulaFunction, its context)
      registry.ts      which functions exist: built-in and custom (`functionNamed`; a custom one replaces a built-in of its name)
      grids.ts         what the functions taking grids share (`GridFunction` in function.ts, `grids: true`: FILTER, SORT, SORTBY, UNIQUE, CHOOSECOLS, TAKE, DROP, HSTACK, VSTACK, SEQUENCE): an argument's grid, lines picked, `stacked` (HSTACK and VSTACK: shorter parts padded with `#N/A` as in Excel, the names each part's side by side, the first part's one under another, an argument that is an error the whole result), `sortOrder` (numbers, text, logical values, errors, empty cells last), `#CALC!` for nothing left
      custom.ts        custom functions (the user's, from Space Lua): definitions checked, a call's throw or wrong result made the formula's error, HELPERS
      builtin/         only functions a formula can call, one per file (sum.ts …), index.ts their list
      values.ts        value types and coercions for functions; `Grid` (rows of columns, each column's name where it came from a table's) and `Result` (a value, a list or a grid), `cellValue` (a cell's one value: several `#SPILL!`), `asValue` (a grid as the list functions taking none get)
```

### Formulas (`formulas/`, `features/formulas.ts`)
- Stored in the cell as the **result plus a hidden `<meta formulas.f='=…'>`**: every renderer and the index see a value; `<meta>` is invisible (verified). Chosen over storing formulas in the metadata row, because a formula addressed by cell position there could, after an edit outside Silverware Table, overwrite a value typed by hand.
- **New formulas need the Store table metadata setting** (they are metadata); with it off a typed formula is saved as text, existing ones keep working (also as calculated columns).
- References: `A1` = first body row (header not counted, as MdTableSheet does), ranges, `[name]` (whole column, without cells whose formulas refer to that whole column: totals), `[@name]` (this row), `[@[a]:[b]]` (this row from column a to b, as Excel's tables write it; a column token with `last`, both ends following renames and moves, one deleted #REF!), with a table's name or not (`prices![@price]`: of its own table its row, of another that table's row of the same number, `rowColumnsValue`; Excel's `Table1[@…]` without `!` is not read, it would be a row's name, `pear[price]`), `[name:2]` for duplicate names. `$` fixes a cell's column or row (`$A$1`, `A$1`, `$A1`, a range's edges each: `Fixed` in references.ts, read by `parseCellName`/`areaOf`; the tokenizer takes a cell with `$` as one name token, as `A1`): it matters only where a formula is filled into other cells (AutoFill); edits of the table move fixed references with their cells as the others, their `$` kept (`followedReference`), as Excel does. F4 in a formula (only there: a text with B2 in it is left alone) cycles the reference at the caret (`cycleFixed`: A1, $A$1, A$1, $A1, a range's ends alike), the reference just pointed at staying the one pointing again replaces; a reference outline dragged or resized keeps its `$` (`dragReference`); a click right before a reference with `$` does not insert one into it (`referenceSlot`); Excel's file gets the `$` as written. Column references are written by **SilverBullet's column key** (`[unit_price]`), the same key a query uses; any spelling with the same key matches.
- Edits made with Silverware Table shift references (rows/columns inserted, deleted, moved, sorted into the markdown, columns renamed); `#REF!` for deleted cells. Edits made in the markdown do not.
- **Other tables**: a table is named in its metadata row (`<meta core.table core.name='prices'>`, its name the title of the table's ⋯ menu (Table without one; while Shift is held in the toolbar too, by the toolbarNames setting), the pencil after it its field, rules in `meta.ts`). Formulas refer to it as `prices!B2`, `prices![price]`, or on another page `[[Page]]prices!B2` (tokens of kind `table`). The evaluator gets a `TableSource` (name, page → Table); a `Book` makes one `Sheet` per table, so other tables' formulas are evaluated too and cycles across tables are `#CYCLE!`. The formulas module builds the source from the page text (`formulas/page.ts` `pageTables`); the pageLinks module caches other pages read with `space.readPage` (re-read for every write that recalculates a table referring to them, and when SilverBullet indexes that page). A write recalculates, in the same edit, the tables that refer to the edited one by name (transitively); their references follow its moved rows/columns, renamed columns and new name (`followTable`). References from other pages do not follow. A page not read (the `pageLinks` module off, or not read yet): `TableSource.unread` makes formulas referring to it keep their stored results (`Book.notRead`, with why; an empty one or an error code is an error). `[col]` leaves out the table's total rows (a cell that refers to its own whole column), so columns of a table line up for `XLOOKUP`.
- **Sources of the space** (decided 2026-11-05/06, docs/silverware-table-views-plan.md, *Step 4: decided*): `@tasks` (its body, as `@tasks[#Data]`) and `@tasks[due]` (a column), a token of kind `source` (tokens.ts; `@tasks!A1` and `@tasks[@due]` refused: a query's rows have no fixed order), a `SourceRef` beside `TableRef` (references.ts; `tablePrefix` writes either in errors), so nothing that follows the page's tables (renames, `Affected`, `references()`, the Excel file's references) takes it for one. The domain gets them through `TableSource.spaceSource` (formulas/page.ts `Elsewhere`, the formulas module's from the sources module's offer, its version in the source's cache key); `Book.notRead` (one pass over the tokens, `formulaOutside`) keeps a result reading a page or a source not read, with why; a source's sheet reads its cells as data (`PLAIN_CELLS`: no formula or name in a value, a hidden tag left out); none of the name `#REF!`. Completion: `@` offers the sources (`sourceChoices`, kind `source` with its columns), `@tasks[` its columns. A pivot reads one (`pivot.source='@tasks'`, `PivotSource.space`, `CalculatedRead.source`), the dialog's Source offering them as a group. In the Excel file a formula reading one is its value.
- **Names in cells** (`names.ts`, the core's; `features/names.ts` the naming UI): one hidden tag in a cell, `<meta core.n='…' core.cn='…'>`, kept by the cell editor, paste and Delete. `core.n` names the line the cell heads: in a header the column's name, apart from its header text (named by the pencil in a menu's title: `Feature.menuNaming`; `columns.ts` finds it first, `columnIdOf` writes it, so references and the stored sort use it whatever the header says; verified that SilverBullet leaves `<meta>` out of the column key). In a body cell `core.n` is the row's name (`pear[price]`, in the first cell or wherever a column move took it; unique in the table; bare, `pear` is the row's cells as a range, as `[price]` a column's, all of them: from a formula in that row #CYCLE! (decided 2026-10-24: leaving the formula's own cell out made the same formula give one result in its row and another elsewhere), a cell's name going first: `rowValues` in evaluate.ts; in Excel's file the row's run), and `core.cn` names the cell for formulas, unique in its table (2026-10-22; before, on the page): `vat` is the formula's own table's only, another table's is `prices!vat` (a `named` node with its `table`), on another page `[[Page]]prices!vat`; so another table's cell needs that table named (nothing names it by itself: a name is metadata written into the table). A bare name of another table's cell, or `[[Page]]vat` (as formulas written before have them), is `#NAME?` saying how to write it (`namedElsewhere` in evaluate.ts, through `TableSource.cellsNamed`), and saving the formula writes it so (`qualifyCellNames` in autofix.ts, after the slip fixes) where one named table of the page has the name; nothing rewrites formulas not edited. Tables are recalculated for each other by table names only (`Affected`): a bare name is no reference to another table. While typing, the list offers the table's own cells bare, other named tables' as `table!name`, and after `table!` that table's cells alone. Names are the core's (it reads columns by them), written and read through host functions (`withColumnName`, `rowNames`…); the formulas get them through `FormulaCells`. A last row with one named empty cell is no metadata row: that is told by its `core.table`. Both names of a cell go in one tag. Names move with their cells, so references by name never need rewriting.
- **Custom functions** (the user's own) are JS, not Lua: a module of the space (`export default [ … ]`, or a function given HELPERS that returns the list), the built-in functions' form, given with `silverware.table.defineFunctions(js.importFromSpace(…))` in Space Lua. Lua was set aside: a Lua function called from JS returns a Promise as soon as it uses SilverBullet's standard library (`ipairs`, `table.insert`, `table.concat` did, verified), and formulas are calculated synchronously (on every view, in the write step); a Lua function would need results kept by arguments and waited for before writes. Verified: JS objects passed through Lua (and config) come back the same objects; `js.importFromSpace` gives the same module for the same path (the browser's module cache) and unwraps a sole default export. The API is a `-- priority: 50` block of its own page, `silverware-table-api.md` (installed beside the library page, listed in its `files:`, as SilverBullet copies every file there next to it: `plugs/configuration-manager/libraries.ts`; the global `silverware.table`, as SilverBullet's `command.define` / `aggregate.define` APIs are blocks of high priority), so scripts of priority 0 can call it; each time Space Lua loads, the scripts' definitions replace those of before, which stay until the first of them (a write meanwhile, or a table shown, still has them; a function no script defines any more stays until a reload), and it imports the same module the main block inits. A mistake in a definition is a notification (SilverBullet's `error` has no level, so it would point at the library page, and it would stop the rest of the user's script). When definitions change (`tablesChanged`, not when a table renders anew: an edit does not change them), tables calling custom or unknown functions are checked again (`callsCustomFunctions`, the formulas module's recheck): one not defined keeps its result as written, Recalculate highlighted. A reference is passed to custom functions as to the built-in ones, a one-cell list for one cell. Names that read as a cell (`LOG2`, CELL_RE) or TRUE/FALSE are refused.
- Built-in functions live one per file in `formulas/builtin/` (only functions there: what they share is beside the folder); a test requires each one's syntax and description in the library page's Functions table. `call(args, context)`: the context is where the formula is calculated (`row`, `column`, as A1 counts), which `ROW()` uses and the others leave out; a result depends on the arguments and the context only. `ROW(reference)` is left out on purpose (in a spreadsheet it mostly works around what table-relative rows give here). *Insert numbered column left* (the formulas module's, the `insert` slot of `lineMenu`, after *Insert*) adds a column `#` of `=ROW()`, a calculated column. There is no `INDEX` function.
- **Which functions are built in**: a function is added only when no existing function or the formula language already covers it (no VLOOKUP/HLOOKUP/MATCH/INDEX: XLOOKUP; no CONCATENATE: CONCAT and `&`; no SUMIF/COUNTIF/AVERAGEIF: the -IFS ones; no compatibility duplicates). Names are plain, without dots, with the modern behaviour: RANK is RANK.EQ, STDEV is STDEV.S, CEILING and FLOOR are CEILING.MATH and FLOOR.MATH (significance optional, its sign ignored), NETWORKDAYS and WORKDAY without .INTL. The -IFS conditions are Excel's (`criteria.ts`), not the filter row's syntax, so formulas copied from a spreadsheet work. Operators on ranges work cell by cell (`cellByCell` in evaluate.ts: a range and a value, or two ranges of the same size, give a range), so `TEXTJOIN(", ", TRUE, "**" & [name] & "**")` and `SUM([qty] * [price])` work as in Excel 365; functions taking one value (`IF`, `ROUND`) still take one, and a cell's result must be one value. No spilling, decided: spilled cells would be values in the markdown needing a mark of their source (else typed data gets overwritten), spilling lists of varying length (FILTER, SORT, UNIQUE) would add and remove rows among the records (sorting, filters, pins, references, undo), and Excel refuses spills in its tables too (#SPILL!). A value per row is a calculated column; a list is SilverBullet's query; a table generated whole from one formula in its metadata row was offered, not done. An argument left out between others (`XLOOKUP(a, b, c, , -1)`) is a null literal, which functions take as not given (a reference to an empty cell is a one-cell list, so it is told apart); a trailing one (`SUM(A1,)`) is not read, so autofix does not complete `=SUM(A1,` to it. Rounding functions take the noise of binary fractions off first (`tidy` in arguments.ts: 0.29 * 100 rounds down to 29); MOD, CEILING, FLOOR and MROUND of a time give a time (`MOD([@end] - [@start], 1)` for a shift past midnight).
- **Dates are ISO text** (`2025-11-06`, `2025-11-06 14:30[:15]`), not spreadsheet serial numbers: results are written into the markdown, and a serial number there would be unreadable, invisible to queries and not a `#date`. `formulas/dates.ts` reads and writes them on a clock without time zone (UTC arithmetic on the written fields); `+`/`-` with a date work as in a spreadsheet (days, date − date = days). Times of day are text too (`14:30`, what `TIME` gives, not a fraction of a day); date + time is the date at that time; the `#time` type also shows fractions of a day (pasted from spreadsheets). `TODAY()`/`NOW()` are written when calculated and show as stale (*Recalculate*) when out of date. The evaluator is synchronous; values are errors-as-values (`FormulaError`).
- Compared with MdTableSheet (malys): it locates a formula's table by searching the formula text in the index (fragile, stale until re-indexed, no chaining, results not visible elsewhere). Silverware Table evaluates from the markdown model it already has.

### Views (decided with the user 2026-11-06, docs/silverware-table-views-plan.md)
- **Calculated by the formulas, in their order**: a table calculated from others (a view, a pivot: `cells.calculated`, a `CalculatedBy` given by the formulas module from the view and pivot modules' `CalculatedOffer`) is read by the `Book` (formulas/evaluate.ts) as calculated now, written as its module would write it (its renamed headers): a table reading it follows its sources in the same calculation. What it reads it gets through `CalculatedRead` (a formula evaluated as its own, or another table as the formulas have it now: `Sheet.withResults`, in the same book so cycles are seen). The formulas module asks the modules named in its `CALCULATING` for their `CalculatedOffer` (as it asks `pageLinks` by name): a new kind of calculated table is one more name there. The pivot was moved onto it on 2026-11-06 (a table reading a pivot was written only by its own next write); its own `writeStep`, `otherTablesWritten` and `prepareWrite` went (pageLinks reads its source's page, as it reads any table's). A view reached again while it is calculated is `#CYCLE!` (told by its page and name, `viewKey`, whichever object of its table a caller holds); its formula reading its own cells (bare references, its own name) is `#CYCLE!` too, a name of no cell of its own `#NAME?` as anywhere. One that cannot be calculated is its error for the formulas reading it and writes nothing (the view stays as it was). `forFormulas` includes a view's formula, so what it refers to (`referredTableNames`, `referredPages`: pageLinks reads its pages) is the table's.
- **A write**: `otherTablesWritten` finds every table the edit affects first and follows their references to the edited table (a calculated table's definition through its `follow`), then calculates each over the page as followed; computed so, a table below a view whose formula followed a rename reads the view as it follows (it read `#REF!` when tables were calculated one by one, bottom up). A view's own write (its Refresh, its settings) is calculated in the formulas' `writeStep`.
- `formulaPages` reads a page from any table token (`[[Page]]tasks![#Data]` was missed).

### Formulas from Space Lua (decided with the user 2026-11-05)
- **Values for Lua, text for a page: two functions each time.** A `${…}` renders what it is given as markdown (a list a block, a list of records a table, `nil` the word, `#REF!` a hashtag: *What a `${…}` shows*), while a script wants values. So `evaluate` gives values and `evaluateText` text as a cell shows it, `errors` records and `errorsText` records of markdown; one function with an option was set aside, the name saying what it gives.
- **An error is `nil` and `{ code, detail }`**, Lua's way, not the code as a text: no text starting with `#` is taken for an error. Inside a list, a cell's error is that record in its place, the other values kept; `""` for an empty cell in a list (a `nil` would end it for `ipairs` and `#`), `nil` for one empty value.
- **`evaluateText` escapes errors only**, as cells write them (`\#REF!`): a `${…}` shows what its cell shows; a text a formula makes (`="#"&"tag"`) stays as typed text would.
- **An alias for each function** (`evaluateAlias`, `evaluateTextAlias`): an alias is more than a short name, its calls' formulas are followed and completed, which a `local` name in a script is not.
- **A page is named as SilverBullet's Lua API names one** (`"Budget"`, `editor.getCurrentPage()`), not `[[Budget]]` (a link's form) nor `[Budget]` (a column in formulas); filters later as an options table after it.
- **Each part where it belongs**: the index and the pages' texts are the Lua's (the JS has no query, and a `${…}` follows what its Lua read), whether a cell holds a formula and a table's errors the formulas module's (its attribute is known to no one else), the records `index.ts`'s. The command is Lua over the public API.
- `errorsText` with none is the line *No formula errors*: an empty result would not tell no errors from nothing calculated. A link or the command puts the cursor in the cell (its offset in the markdown), not at its row's start.
