# Silverware Toolbar

A toolbar by the text selected (as Notion's), or docked over the on-screen keyboard or under SilverBullet's top bar: favourite actions as icons, *Turn into* (block formats), `…` the popup of every action with a search. The command *Silverware Toolbar: Show actions* (`Ctrl-Shift-q` by default) opens the popup; without a selection the toolbar shows at the caret. Prefix `swb-`, settings and API `silverware.toolbar.*`.

Plan, decisions and their dates: [docs/silverware-toolbar.md](../docs/silverware-toolbar.md) (*Status and next* first; the sections of 2026-11-10 for toolbars, the switch, parameters, migrations, slash). Icons: [silverware-icons/CLAUDE.md](../silverware-icons/CLAUDE.md).

## Mental model

- **The core knows no module, no format, no action by name.** Modules (`src/modules.ts`, in order, created only where `silverware.toolbar.modules.<name>.enabled`) give actions; their actions are asked for each time they show, so definitions made later count. Custom formats and actions (`defineFormats`, `defineActions`, the API page) go through the same checks as built-in ones; a custom one of a built-in name replaces it in place.
- **An action** (`core/action.ts`): id `formats.<name>` / `actions.<name>` / `commands.<name>`, and one of `edit` (gives a `Change`, the core writes it), `perform` (does something through `ActionEditor`, the core writes nothing), `choices` (a list: Turn into) or `panel` (its own UI: the emoji picker). `listed: false`: found by the popup's search only (the commands). `touchOnly`: left out unless the device is a touch screen, the settings offering it for a toolbar a finger may show.
- **Writes**: the context is read anew before an action runs; its change is one `replaceRange`, and nothing is written where the page's text changed since it was read. The selection after a change is marked in the text written by two Private Use Area characters (`core/cursor.ts`, the last pair counts).
- **Formats domain** (`formats/`, pure, knows no format by name): block formats (Turn into, line by line) and inline ones (toggled around the part, through other formats' markers). `formats/builtin/` holds only formats, one per file. `wordAtCaret` (on by default): a caret touching a word stands for it as if selected; the inline and clear modules hand that context to the engines, which know nothing of it.
- **Toolbars** (`core/toolbars.ts`, `silverware.toolbar.favorites`): a list of up to 5 `{ name, useFor, placement, show, rows }`, names unique ignoring case. `useFor`: the ways of working (`"click"`, `"touch"`) it shows for; every way has exactly one toolbar (`normalizedToolbars`), a toolbar for none is kept to switch to. Where (`selection`, `bottom`, `top`) and when (`always`, `writing`, `selection`) are the toolbar's, not a device's. Defaults *Float* (Click) and *Docked* (Touch; without the gestures module none, Float for both).
- **Favourites** (`core/favorites.ts`): rows of items, read leniently (`favoriteItemOf`: what is no item is left out). An action's item `{ id, show, width, pin, icon, label, args }`; `{ type = "separator" }`; or a kind's item (`core/items.ts`: `ItemKind` from a module, its `slots` holding action ids, `fields`, `ownLook`, `check`, `render`). Kinds now: the gestures module's `gesture`, the snippets module's `snippet`. A kind no module on gives, or a required slot without an action: the item left out. An id no action has: skipped in the bar, dimmed in the settings. `pin` matters only docked (each row a line, pinned items at its ends).
- **`…` (`actions.more`) is an item like any other**; a toolbar without it gets it pinned at the end and the settings warn.
- **Action parameters** (`params`, `args`; decided 2026-11-10): an action declares `params` (key, label, `choices` or text, `refersTo`) and `describe`; a favourite gives `args` (texts by key). The controller binds them with `withArgs` (functions given the values, `choices` dropped so it runs), so bar, popup and kinds know nothing of parameters. Without args the action gets `NO_ARGS`. The settings' add search offers such an action alone, without its choices, and opens its panel. Values are always texts.
- **The switch of toolbars** (`core/switch.ts`, `actions.switchToolbar`, the core's own): with `args.toolbar` it switches at once; without, its choices list the toolbars. The new `useFor` is written to CONFIG in the background (`keepSwitched`, through the one write queue `queued` that the dialog's Save and migrations use too); a toolbar renamed in the dialog takes the args that `refersTo` it along (`withArgRenamed`).
- **Own icons**: `iconOf` keeps an `<set>:<name>` reference whole, else the first `MAX_ICON` (3) graphemes. Every own icon (item, slot, snippet, settings) is drawn by `Icons.markup(value, OWN_ICON)` (base `swb-own`, box `swb-own-icon`). `Icons` comes from `iconsOf(bridge.icons)`, made once in index.ts and handed to modules (`ModuleHost.icons`), controller and dialog. The Emoji action is Silverware Icons' picker with `sets: ["emoji"]` (it writes into the page). The isolation test refuses imports of any other plugin's code.

## Settings and CONFIG

- Read once at start (`bridge.ts readSettings`): a change applies on reload, except favourites saved by the dialog (the toolbar is started anew) and a switch.
- **The dialog edits purely**: `settings/favorites.ts` holds the edits as pure functions; nothing is written until Save; a module or the key changed means *Save and reload*.
- **Where it writes** (index.ts `saveSettings`): the playground's `bridge.saveSettings`, else CONFIG through shared/configpage.ts: scalars (key, modules, version) in the Configuration Manager's block, the toolbars (a table) in the toolbar's own block (`OWN_MARKER`), as the Configuration Manager reads no table back and rewrites its block from what it read. A value `undefined` is taken out of both blocks (keys of an older model).
- **Migrations** (`src/migrations/`): one file per model version (`2-toolbars.ts`: version 1's per-device favourites, placement and show become toolbars), listed in `MIGRATIONS`. `silverware.toolbar.version` unset is 1. Settings are migrated as read (`Settings.migrated`) and written back once with the version (`writeMigrated`); where that cannot be written, the dialog writes it with its next Save. Adding one is a file and a line.
- A test keeps the default favourites equal to the init page's `config.define`.

## Gotchas

- **The key**: SilverBullet handles it as the command's `key` (init page: `config.get("silverware.toolbar.shortcut", …)`). Not `Mod-.` (SilverBullet's chord prefix), not `Cmd-Shift-q` on a Mac (logs out).
- **A press on the toolbar keeps the editor's selection and focus**: its mousedown is prevented. Touch: `touch-action: pan-x` leaves a sideways move to the docked bar's scroll.
- **Docked, choices (Turn into) open in the popup at their level**, not in a list under the button: the popup's search keeps the on-screen keyboard and hides the system's selection menu; a list that took the keyboard closed it, one without it lay under that menu (tried on a phone, 2026-10-26).
- **Room for a docked toolbar**: its height as `--swb-docked-top` / `-bottom` on `html`, the style page padding `#sb-editor` (border-box, as SilverBullet's height is 100%). A bar by the selection alone lies over the text, else the editor jumps. Hidden by a press elsewhere in the editor (a table's cell edited) the room stays: the editor jumping under the finger broke the table's touch tests in CI.
- **Esc does not hide a toolbar that shows always or while writing** (`persistent`): Esc is the editor's then. Shown by a selection or at the caret, Esc and a key typed hide it.
- **SilverBullet's commands** (`modules/commands.ts`) are read at start, when Space Lua is still loading (the user's missing): read again on `system:ready` (`scriptsLoaded`), as the toolbar first shows after each load of Space Lua (`Controller.reloaded`), after a failure (`RETRY_MS`) and every `FRESH_MS` as asked.
- A "/" written through the editor API opens no completion: the slash module writes it, a space before where `slashCommandRegexp` would not match, then calls `editor.startCompletion` (asked first, so a release without it gets no stray "/"). The playground has its own slash completion.
- **Hiding the keyboard** (`core/keyboard.ts`): the VirtualKeyboard API with the policy `manual` until the next tap, the text keeping focus and selection; without it (Safari on iOS) the text is blurred.
- Everything assumed about SilverBullet's DOM is in `src/dom.ts`.

## Verified in SilverBullet

- Its source (2026-10-26): `editor.getSelection/setSelection/replaceRange/getText`; no selection event and no screen position, both come from the DOM. Dialogs are `<dialog class="sb-modal-box">` with plain inputs, so the page's only CodeMirror is its text (`.cm-content`, outside widgets marked `contenteditable=false`).
- By the UI tests against 2.12.1 (2026-10-26): the key from `config.get`, the toolbar by a selection and at the caret, `editor.focus`, settings saved into CONFIG and read back after a reload, `editor.reloadUI`, SilverBullet's confirm dialog.
- Docked line, in order (`core/dock.ts`): the top of `.sb-keyboard-bar` where it shows (SilverBullet's main since 2026-10, no release yet; on with the UI option `keyboardBar`, per device, toggled by its command *Editor: Toggle Keyboard Bar*; the settings offer turning it off where `editor.getUiOption("keyboardBar")` is on, on a touch screen); else the bottom of `#sb-root` where `html.sb-viewport-tracked` pins it above the keyboard (client/lib/keyboard_viewport.ts of main: the VirtualKeyboard API's rectangle did not match on a phone); else the keyboard's top where `navigator.virtualKeyboard.overlaysContent` (window and visual viewport keep their size, `geometrychange` tells it); else the visual viewport's bottom. SilverBullet renders its bar in or out after those events, so a MutationObserver watches while docked. Held by its bottom edge: rounded apart, a line of the page showed under it.
- `#sb-editor` is the editor between the sidebars: docked, the toolbar stays within it.
- Room kept for the docked bar, checked as a phone in the local SilverBullet (2026-10-27).
- Underline as `<u>…</u>` shows underlined (local build). The tag format follows SilverBullet's `tagRegex` of 2.12.1 (`#<several words>` where one word cannot be a tag).
- `editor.startCompletion` exists in 2.12.1; `slashCommandRegexp` is `([^\w:]|^)\/[\w#-]*` (client/plugos/hooks/slash_command.ts).
- Not checked yet: the toolbar over the top bar and with the Tiniri theme by eye, a real phone (Chrome's emulation only).
